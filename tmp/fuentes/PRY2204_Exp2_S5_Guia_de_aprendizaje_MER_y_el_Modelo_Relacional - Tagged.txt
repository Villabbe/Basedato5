Un modelo relacional (MR) es representación lógica de los datos, basada en la organización 
de la información en tablas (o relaciones), donde cada tabla está compuesta por filas (tuplas) 
y columnas (atributos). Este modelo se fundamenta en conceptos clave como claves 
primarias, utilizadas para identificar de manera única cada tupla dentro de una tabla, y 
claves foráneas, que permiten establecer relaciones entre tablas diferentes. 
A lo largo de esta semana, aprenderemos a transformar modelos conceptuales a modelos 
lógicos, cómo mapear las entidades, relaciones y atributos de un modelo ER (MER) en 
tablas, columnas y claves de un modelo relacional (MR), respetando las reglas de integridad 
y garantizando la consistencia de los datos. Y así, nos aproximaremos al modelo físico de la 
base de datos.

Modelo Relacional 
Es un conjunto de una o más tablas estructuradas en registros (líneas) y campos 
(columnas), que se unen entre sí por un campo en común. Al campo que une dos tablas se 
le denomina ID, identificador o clave. A esta manera de construir bases de datos se le 
denomina modelo relacional. 
Las bases de datos relacionales pasan por un proceso al que se le conoce como 
normalización de una base de datos, el cual es entendido como el proceso necesario para 
que una base de datos sea utilizada de manera óptima.
Una base de datos se compone de varias tablas y relaciones. Es importante que consideres 
que no pueden existir dos tablas con el mismo nombre. Cada tabla es a su vez un 
conjunto de campos (columnas) y registros (filas).
La clave primaria es la clave principal de un registro dentro de una tabla.
La relación entre una tabla padre y tabla hijo es por medio de las claves primarias y claves 
foráneas o ajenas. Las claves ajenas se colocan en la tabla hija, contienen el mismo valor 
que la clave primaria del registro padre.

Terminología de los Modelos Relacionales
Cuando nos referimos a los modelos relacionales, es necesario que comprendas los 
siguientes términos:
 Relación: Corresponde con la idea general de tabla.
 Tupla: Corresponde con una fila.
 Atributo: Corresponde con una columna.
 Cardinalidad: Número de tuplas (m).
 Grado: Número de atributos (n).
 Dominio: Colección de valores de los cuales el atributo obtiene su atributo.
 Clave Primaria: Identificador único de una tupla.

Es importante definir las claves, ya que en una relación no hay tuplas repetidas, éstas se 
pueden distinguir unas de otras, es decir, se pueden identificar de modo único. La forma de 
identificarlas es mediante los valores de sus atributos.
 Clave candidata: conjunto de atributos que identifican en forma única cada tupla de 
la relación. Es decir, columnas cuyos valores no se repiten para esa tabla. 
 Clave primaria: clave candidata que se escoge como identificador de las tuplas. Se 
elige como primaria la candidata que identifique mejor a cada tupla en el contexto de 
la base de datos. Por ejemplo, un atributo con el RUT sería clave candidata de una 
tabla de clientes, aunque si en esa relación existe un atributo de código de cliente, 
este sería mejor candidato para clave principal, porque es mejor identificador para ese 
contexto. 
 Clave alternativa: cualquier clave candidata que no sea primaria y que también 
puede identificar de manera única una tupla. Al momento de crear la relación como 
tabla en la Base de Datos se debe definir una constraints de tipo UNIQUE. 
 Clave externa, ajena o foránea: atributo cuyos valores coinciden con una clave 
candidata (normalmente primaria) de otra tabla.

Una restricción es una condición que deben cumplir los datos de la base de datos. Las 
restricciones propias de las bases de datos relacionales son:
 No puede haber dos tuplas iguales.
 El orden de las tuplas no es significativo.
 El orden de los atributos no es significativo.
 Cada atributo sólo puede tomar un valor en el dominio en el que está inscrito.
Las restricciones incorporadas por los usuarios son:
 Clave primaria (PRIMARY KEY o PK): hace que los atributos marcados como clave 
primaria no puedan tener valores repetidos. Además, obliga a que esos atributos 
deben tener un valor. Si la clave primaria la forman varios atributos, ninguno de ellos 
podrá estar vacío. 
 Unicidad (UNIQUE): impide que los valores de los atributos marcados de esta forma 
puedan repetirse. Esta restricción debe indicarse en todas las claves alternativas.
 Obligatoriedad (NOT NULL): obliga que el atributo marcado de esta forma debe 
tener un valor, es decir impide que pueda contener el valor nulo (null). 
 Integridad referencial (FOREIGN KEY o FK): sirve para indicar una clave externa ó 
foránea. Cuando una clave se marca con integridad referencial no se podrán 
introducir valores que no estén incluidos en los atributos relacionados con esa clave 
de la relación “padre”. Esto último causa problemas en las operaciones de borrado y 
modificación de registros, ya que si se ejecutan esas operaciones sobre la tabla 
principal quedarán filas en la tabla secundaria con la clave externa sin integridad.

Una clave primaria es un campo que identifica un solo registro (fila) en una tabla.

La tabla solo puede tener una clave primaria. Todos los campos pueden ser clave primaria. 
Sus valores no pueden repetirse ni ser nulos. Al definir un campo como clave primaria, 
automáticamente Oracle lo convierte a "not null".
En ocasiones una clave primaria debe componerse por más de un campo. Se conocen como 
claves primarias compuestas y las que tienen solo un campo se conocen como claves 
primarias simples.
En el ejemplo, la tabla ARRIENDO tiene un campo numero_departamento que es la clave 
primaria. Consideremos el departamento 103 que fue arrendado en enero 2020. Si ese 
departamento vuelve a arrendarse en marzo 2023 generaría un error de clave primaria 
duplicada ya que el numero 103 se estaría repitiendo.

Clave Foránea
Un campo que no es clave primaria en una tabla y que además sirve para enlazar sus 
valores con otra tabla en la cual es clave primaria. Estos campos se denominan clave 
foránea, externa o ajena.
Las claves foráneas y las claves primarias deben ser del mismo tipo para poder enlazarse. 
Si modificamos una, debemos modificar la otra para que los valores se correspondan.
Debemos tener cuidado con las claves foráneas. Si modificamos el tipo, longitud o atributos 
de una clave foránea, ésta puede quedar inhabilitada para hacer enlaces.

De la noción que hemos dado de clave foránea, se pueden extraer tres consecuencias: 
1. Si una clave foránea (FK) referencia una clave primaria (PK) el número de atributos 
de FK y de PK debe coincidir. En el ejemplo anterior, tanto la FK {edificioarea, 
numeroarea} como la PK que referencia {edificio, numero} tienen dos atributos. Si no 
sucediese así, no sería posible que los valores de FK existieran en PK.
2. Por el mismo motivo, se puede establecer una correspondencia, una biyección, entre 
los atributos de la clave foránea y los atributos de la clave primaria que referencia. 
3. Así también, a ‘edificioarea’ le corresponde el atributo edificio, y a ‘numeroarea’ le 
corresponde el atributo ‘numero’. 
4. También se deduce de la noción de clave foránea que los dominios de sus atributos 
deben coincidir con los dominios de los atributos correspondientes a la clave primaria 
que referencia. Esta coincidencia de dominios hace que sea posible que los valores 
de la clave foránea coincidan con valores de la clave primaria referenciada.

Cómo se transforman las entidades
La transformación del modelo conceptual al modelo lógico implica trasladar la representación 
abstracta de los datos, descrita en términos de entidades, atributos y relaciones (modelo 
entidad-relación o ER), a una estructura que pueda ser implementada en un sistema de 
gestión de bases de datos relacional (RDBMS). Este proceso tiene como objetivo definir 
cómo se organizarán y almacenarán los datos en tablas, respetando las restricciones de 
integridad y asegurando que el diseño sea funcional y claro.
Entidades fuertes
 Toda Entidad del Modelo E/R se transforma en Relación o Tabla en el Modelo 
Relacional.
 Los atributos de las entidades del Modelo E/R se transforman en atributos o 
columnas de la Relación en el Modelo Relacional. 
 Los atributos Identificadores Únicos de las Entidades del Modelo E/R se 
transforman en la Clave Primaria (PK) de la Relación del Modelo Relacional.
 Por lo general el formato del nombre de la clave primaria es PK_nombretabla. 
La entidad EMPLEADO del Modelo E/R se transforma en la Relación EMPLEADO en el 
Modelo Relacional. El atributo identificador único de la entidad se transforma en la 
Clave Primaria de la Relación (marcada con una P en el Modelo Relacional gráfico).

Relaciones de 1:N
La Relación del lado muchos (tabla relacionada) incluye como clave externa o foránea 
(FK) las columnas que forman la clave primaria de la Relación del lado uno (relación 
principal). A esta clave foránea se le debe asignar un nombre.
Por lo general el formato del nombre de la clave foránea es 
FK_tablarelacionada_tablaprincipal.
En el Modelo Relacional, la punta de la flecha indica la tabla principal que contiene la(s) 
columna(s) de clave primaria que con referenciadas por la tabla relacionada. La columna 
clave foráneas además aparece marcada con una F.
En el ejemplo, la columna codigo de la relación DEPARTAMENTO es incluida como 
columna de la Relación EMPLEADO y además es Clave Foránea.

Relaciones N:M
Para las relaciones Muchos a Muchos del modelo E/R que no pudieron ser eliminadas se 
debe generar una Relación Intermedia en el Modelo Relacional a la cual se debe asignar un 
nombre adecuado.
La Relación de intersección o intermedia contiene dos claves externas (claves foráneas), 
cada una referencia a la clave primaria de las tablas originales.  Ambas claves externas 
(foráneas) además componen la clave primaria de la Relación intermedia a la cual se le 
debe asignar un nombre adecuado. 
En el ejemplo, se crea la Relación intermedia ASIGNATURA_DICTA con las columnas de 
claves primarias de las Relaciones ASIGNATURA y PROFESOR (ambas columnas son PK y 
FK).

Relaciones 1:1
Las relaciones uno a uno en el MER son poco comunes. En muchos casos puede implicar 
que las dos entidades son en realidad una sola y se deben unir.
Si se debe mantener la relación 1:1, se utiliza la o las columnas que conforman la clave 
primaria de la otra como clave foránea en una de las relaciones del Modelo Relacional.
En el caso de que una entidad participe opcionalmente en la relación, entonces es el 
identificador de esta entidad el que se utiliza como clave foránea en la Relación que 
representa a la otra entidad.
En el siguiente ejemplo, la relación del EMPLEADO con su CONYUGE es opcional, por lo 
tanto, al transformar a modelo relacional la clave primaria de EMPLEADO, se convierte en 
una columna más de CONYUGE y además es clave foránea.

Relación de Exclusividad
Los arcos representan una columna de clave foránea en la Relación principal. El Diseño 
de Arco explícito crea una columna clave foránea para cada relación incluida en el arco.
En el ejemplo, la columna codigo de la Relación EMPRESA y la columna numrut de la 
Relación PERSONA se transforman en columnas de claves foráneas de la Relación

Jerarquías / Subtipo en una Relación
Consiste en diseñar una tabla para el supertipo con toda la información de los subtipos. En 
otras palabras, la tabla resultante contiene las instancias de todos los subtipos. Es apropiado 
cuando los subtipos tienen pocos atributos y la consulta de los datos suele incluir datos de 
distintos subtipos. 
Los pasos para este diseño son:
 Crear una Relación o tabla para el Supertipo.
 Crear una columna “tipo” para identificar a cuál subtipo pertenece la fila o tupla.
 Crear una columna para cada uno de los atributos del supertipo.
 Crear una columna para cada uno de los atributos de los subtipos.
 Crear columnas claves foráneas para cada una de las relaciones del supertipo.
 Crear columnas claves foráneas para cada una de las relaciones de los subtipos.
En el ejemplo, se crea la Relación VEHICULO con los atributos del supertipo y subtipos. 
Además, se crea la columna tipo_vehiculo para poder saber si la información que se 
almacenará será de un camión o remolque.

Jerarquías / Subtipo en Relaciones Separadas
Consiste en convertir los subtipos en Relaciones diferentes, una para cada subtipo. Cada 
tabla tendrá instancias solo de ese subtipo. Se usa este diseño cuando los subtipos tienen 
muchos atributos y relaciones específicas.
Los pasos para este diseño son:
 Crear una Relación o tabla para cada subtipo.
 En cada tabla de un subtipo crear las columnas para los atributos del supertipo.
 En cada tabla de un subtipo crear columnas claves foráneas para cada relación del 
subtipo.
 En cada tabla de un subtipo crear columnas claves foráneas para cada relación del 
supertipo.
En el ejemplo, se crea las Relaciones CAMION y REMOLQUE cada una con sus atributos y 
además con los atributos del supertipo incluyendo su clave primaria.

Tipos de entidades, tipos de relaciones y claves
Para cada tipo de entidad se crea una relación con el mismo nombre y conjunto de atributos. 
Por ejemplo, en el caso de la BD de matrícula de alumnos en DUOC UC resumidas, los tipos 
de entidades dan lugar a las siguientes relaciones: 
 ALUMNO(rut, ApellidoPaterno, ApellidoMaterno, nombres, direccion, celular, idComuna) 
 ASIGNATURA(Codigo, Título, numCreditos) 
 PROFESOR(rut, ApellidoPaterno, ApellidoMaterno, nombres, direccion, Telefono) 
 SALA(Edificio, Número) 
En cuanto a las relaciones, para cada tipo de relación “R” se crea una relación que tiene 
como atributos: 
 Los atributos de la clave primaria de cada tipo de entidad que participa en la relación. 
 Los atributos de la propia relación. 
En ocasiones hay que renombrar atributos para evitar tener varios con el mismo nombre. 
Como ejemplo, en el caso de la BD los tipos de relación dan lugar a las siguientes 
relaciones: 
 MATRICULA(rutmatricula, Código, Nota) 
 SUPERVISOR(rutSupervisor, rutmatricula) 
 IMPARTE(rutsupervisor, Código, Edificio, NumSala) 
Si nos fijamos en la relación SUPERVISOR, se han renombrado los atributos rutSupervisor 
para indicar el papel de cada uno de ellos en la relación y además evitar que se use el 
mismo nombre para más de un atributo y así, no tener ningún tipo de inconveniente en un 
futuro cercano cuando queramos consultar los datos que ahí se guardaron.

Sobre las claves, hay dos casos: 
1. La relación proviene de un tipo de entidad en el esquema E-R. La clave es la misma 
que la del tipo de entidad. Por ejemplo: 
ALUMNO(rut, nombreCompleto, direccion, idComuna) 
2. La relación proviene de un tipo de relación en el esquema E-R. Si la relación R es un 
tipo de relación entre varios tipos de entidades, se va a construir una relación bajo el 
modelo E-R a partir de R con los atributos que forman clave primaria en todas las 
entidades participantes, más los propios de R. De ellos formarán clave primaria las 
claves primarias de cada una de las entidades participantes. Por ejemplo: 
MATRICULA(rut, Codigomatricula, rutAlumno)

Restricciones de integridad
Hemos visto cómo se traducen las claves de los tipos 
de entidades y cómo aparecen claves en la 
traducción de los tipos de relaciones. Sin embargo, no 
es el único tipo de restricciones de integridad que 
aparece automáticamente al traducir un esquema E-R 
en otro relacional. Hay dos: restricciones de 
integridad referencial y las restricciones de 
participación total. 
Las claves y las restricciones de integridad referencial 
son características que se utilizan directamente en 
casi la totalidad de los SGBD relacionales. Estos 
sistemas se ocupan automáticamente de que no se violen estas restricciones. Sin embargo, 
no ocurre lo mismo con las de participación total y otras restricciones. Profundicemos en 
estas restricciones: 
Restricciones de integridad referencial 
Al traducir un tipo de relación R, en cualquier instancia de R se debe cumplir que los valores 
de los atributos que hereda de una entidad deben aparecer previamente en el conjunto de 
entidades. Por ejemplo, si tenemos dos entidades, una PADRE y otra HIJO, donde 
identificamos al PADRE con el campo rutPadre y al HIJO con el campo rutHijo, está claro 
que en la relación no puede aparecer un valor del rut de un padre o de un hijo que no estén 
previamente en el conjunto de entidades PADRE e HIJO. Es decir, a HIJO no podemos 
asociarle un padre que no existe en la tabla PADRE(rutPadre), lo mismo a un padre, no se le 
puede asociar un hijo que no esté en la entidad HIJO (idHijo). 
Es necesario, por tanto, imponer una restricción de integridad referencial entre los atributos 
clave heredados de una entidad con los clave de esa entidad. 

PAGINA 31
31
En este ejemplo, se podría expresar: 
PADRE.rutPadre ⊆ HIJO.rutHijo 
HIJO.rutHijo ⊆ PADRE.rutPadre 
Restricciones de participación total 
Cuando cada valor de un tipo de entidad debe aparecer en un tipo de relación, como 
Alumnos en Matrícula, significa que, además de la restricción de integridad referencial 
comentada en el apartado anterior, se debe cumplir que todo valor de rut en ALUMNO debe 
aparecer en el atributo rut de MATRICULA. 
Esto se puede expresar: ALUMNO.rut ⊆ MATRICULA.rut Por otra parte, dado que la 
restricción de integridad referencial sobre esta tabla arroja: MATRICULA.rut ⊆ ALUMNO.rut 
Llegamos a la conclusión de que: MATRICULA.rut = ALUMNO.rut. Es decir, si aparece un 
valor de rut en MATRICULA, también debe aparecer en el atributo rut de ALUMNO, y 
viceversa.

Diseño Físico 
El objetivo del diseño 
físico es la generación del 
esquema físico de la base 
de datos en el modelo de 
datos que implementa el 
Sistema de Gestión de 
Base de Datos (SGBD).  
La transformación de un modelo lógico a un modelo físico en bases de datos implica 
convertir las estructuras definidas en el modelo lógico en estructuras reales que serán 
implementadas en un motor de bases de datos como Oracle, SQL Server, MySQL, etc. Esto 
incluye la definición de las tablas, columnas, tipos de datos, restricciones de integridad y 
otros objetos propios de cada de base de datos como índices, vistas o procedimientos 
almacenados. Es por esto que, un script de Oracle puede no ejecutar correctamente en un 
motor SQL Server, porque cada SGBD en su modelo físico tiene sus propias definiciones. 
En esta asignatura usarás Oracle Cloud como motor de base de datos relacional.

Cierre de la semana
Durante esta semana, nos enfocamos en el 
proceso de transformación de modelos 
conceptuales a modelos lógicos, un paso 
fundamental en el diseño de bases de datos 
que permite implementar estructuras bien 
definidas en sistemas relacionales. 
Revisamos los conceptos básicos de los 
modelos relacionales, clarificando las 
diferentes terminologías entre claves primarias y foráneas, relaciones, cardinalidades, tuplas, 
etc.
Profundizamos en la transformación de modelos entidad relación a modelos relacionales, 
abordando cómo convertir entidades en tablas, atributos en columnas, identificadores únicos 
en claves primarias, relaciones en claves foráneas, cómo manejar la herencia mediante 
estrategias como las tablas únicas, separadas o combinadas. También exploramos la 
transformación de relaciones en sus distintas cardinalidades: 1:1, 1:N y N:M, explicando 
cómo utilizar claves foráneas y tablas intermedias para garantizar la integridad referencial. 
Además, estudiamos las reglas de exclusividad, que imponen restricciones en los datos, 
garantizando que las relaciones excluyentes se implementen correctamente mediante claves 
y restricciones lógicas. 
Finalmente, vimos como transformar modelos lógicos a físicos generando el script con 
Oracle SQL Developer Data Modeler, preparándonos a la próxima experiencia donde 
implementarás bases de datos en Oracle Cloud.
